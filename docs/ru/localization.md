# Локализация

Английский язык является исходным языком документации `nllclw`. Сначала
полностью обновляйте английские файлы, затем переводите текущую английскую
версию.

## Структура файлов

| Путь | Назначение |
|---|---|
| `README.md` | Английский обзор проекта для GitHub. |
| `README.<locale>.md` | Необязательные переведенные README-файлы в корне. |
| `docs/README.md` | Индекс языков. |
| `docs/en/` | Английская подробная документация. |
| `docs/<locale>/` | Будущая переведенная подробная документация. |

По возможности используйте lowercase language tags в стиле BCP 47 для
каталогов: `ru`, `es`, `pt-BR`, `zh-CN`, `ja` и подобные.

## Контракт перевода

- Зеркальте список файлов `docs/en/`, если файл не является только английским.
- Сохраняйте тот же порядок секций верхнего уровня, что и в английском источнике.
- Не меняйте имена команд, переменные окружения, пути файлов, URL, JSON-ключи,
  Zig-идентификаторы и названия протоколов.
- Переводите прозу, заголовки, описания таблиц и поясняющие комментарии.
- Сохраняйте относительные ссылки. Меняйте только сегмент локали при ссылке на
  переведенную страницу.
- Не переводите сгенерированный вывод команд, если это не проза,
  показываемая пользователям.
- Не добавляйте в перевод утверждения, которых нет в английском источнике.
- Обновляйте `docs/README.md`, когда новый языковой каталог полезен
  пользователям.

## Как писать английский для перевода

Качество перевода начинается с английского источника.

- Используйте короткие прямые предложения.
- Предпочитайте активный залог.
- Избегайте идиом, шуток, сленга и культурно-специфичных отсылок.
- Определяйте термин при первом появлении.
- Когда практично, держите одну инструкцию или факт в одном предложении.
- Делайте списки параллельными: начинайте каждый пункт с одного типа слова.
- Избегайте "this", "that" и "it", когда существительное может быть неясным.
- Используйте точные даты вместо относительных дат в долгоживущей документации.
- Делайте скриншоты и диаграммы необязательными; инструкция должна быть
  понятна по тексту.

## Защищенные термины

Не переводите эти термины, если в языке нет широко принятого технического
перевода и точный смысл не сохраняется.

| Термин | Причина |
|---|---|
| `nllclw` | Название продукта и бинарника. |
| Zig | Название языка программирования. |
| Chat Completions | Контракт API провайдера. |
| OpenAI, OpenRouter | Имена провайдеров. |
| WebSocket, Telegram, JSONL, SSE | Названия протоколов или форматов. |
| `NLLCLW_*` | Namespace переменных окружения. |
| `src/`, `docs/en/`, `config.json`, `.env` | Буквальные пути и имена файлов. |
| `shell_exec` | Имя инструмента и граница безопасности. |

## Раскатка на двенадцать языков

При добавлении запланированного набора переводов:

1. Сначала завершите английские правки.
2. Выберите точные locale tags.
3. Скопируйте `docs/en/` в каждый `docs/<locale>/`.
4. Переведите прозу, сохраняя команды, ключи конфигурации, блоки кода и имена
   файлов.
5. Добавляйте переведенные README-файлы в корень только если они поддерживаются.
6. Добавляйте каждый завершенный язык в `docs/README.md`.
7. Проверяйте ссылки внутри каждой локали.
8. Запускайте `git diff --check`.

Не создавайте пустые языковые каталоги. Язык должен появляться в
`docs/README.md` только после появления его точки входа.

## Checklist обновления источника

Когда английская документация меняется после появления переводов:

1. Обновите английский исходный файл.
2. Обновите связанные ссылки README или docs hub.
3. Отметьте, нужны ли такие же изменения переведенным файлам.
4. Держите метрики в [benchmarks.md](benchmarks.md) и snapshot README
   синхронизированными, когда меняется размер бинарника, количество тестов,
   количество исходников или LOC.
5. Запустите локальные команды проверки из [development.md](development.md).
